# RuinCity · 千年之後 —— 設計文件

> 把地球依經緯度切成區塊，用捐款請 AI 畫出每一塊在**人類離開一千年後**的樣子。
> 從臺北 101 開始。哪一塊先蓋好、由哪一家模型來畫，取決於捐款的人。

本文件是規格。程式碼與它不一致時以本文件為準，並同時修正兩邊。

---

## 1. 世界與網格

| 項目 | 規則 | 實作 |
| --- | --- | --- |
| 區塊大小 | **0.01° × 0.01°**（全球 18,000 列 × 36,000 欄） | `lib/world/grid.ts` |
| 名字 | 西南角兩位小數：`25.03_121.56` = 北緯 25.03°–25.04°、東經 121.56°–121.57° | `blockKey` / `parseBlockKey` |
| 原點 | 臺北 101（25.033964, 121.564468）所在的 `25.03_121.56` | `TAIPEI_101`、`ORIGIN_BLOCK` |
| 實際大小 | 隨緯度變：臺北約 1.01 km（東西）× 1.11 km（南北）；赤道 1.11 × 1.11；北緯 60° 0.56 × 1.11 | `blockSizeM` |

**為什麼是經緯度而不是公尺網格**：公尺網格要選投影，而任何投影都只在一個區域內是方的。
經緯度在全球是同一套規則，任何人拿到一個座標都算得出它屬於哪一塊。
代價是區塊大小隨緯度變化 —— 「一塊」是**命名與募款的單位**，不是測量單位。

**整數索引**：`25.03 × 100` 在浮點數是 `2502.9999…`。所有比較都在整數的列/欄上做，
否則剛好落在格線上的西南角（也就是每一塊自己的名字）會被分到隔壁。

極區（|緯度| > 85°）不開放捐款。

## 2. 一塊地圖的一生

### 2.1 狀態

```
尚無捐款 ──第一筆捐款入帳──▶ 建設中 ⇄ 募款中 ──最後一步完成──▶ 已完成（可進入）
                              │
                              └──連續失敗──▶ 施工暫停
```

| 狀態 | 條件（**由帳推導**，不存欄位） |
| --- | --- |
| 尚無捐款 | 沒有任何已入帳的捐款 |
| 募款中 | 施工餘額不夠下一步估價的 1.25 倍 |
| 建設中 | 正在畫，或餘額夠開下一步 |
| 施工暫停 | 連續失敗 3 次，或平台金鑰被拒（等人處理；新捐款入帳不會自動解除，除非暫停原因是等錢） |
| 已完成 | 所有步驟成功；撥付保存費後標記 |

狀態只存兩個事件：`completed_at` 與 `paused_at`。其餘全部由帳推導 ——
狀態欄位會和帳分岔，而帳才是真相。

### 2.2 完成前不能進入

施工中的區塊**只公開四個數字**：

| 數字 | 定義 |
| --- | --- |
| **預計所需 Token** | 建設各步驟的 token：已完成的取實際、剩下的以目前領先的模型估計 |
| **換算金額** | 完成這一塊所需的**募款總額**（含預算書的全部五組支出） |
| **已花費 Token** | 實際用掉的 token（含失敗重來的） |
| **已花費金額** | 實際花掉的錢：token、參考影像、手續費、稅、拒付準備、完工時撥付的保存與分攤 |

另外公開：募款進度、施工進度（第幾步／共幾步、下一步是什麼）、投票結果、預算書、施工紀錄（哪一步由哪個模型畫、用了多少 token 與錢）。**不公開任何一張圖。**

這個限制守在**出圖的 API**（`/api/blocks/[key]/art/...` 未完成回 403），不只是頁面不顯示 ——
圖的網址是猜得到的。

### 2.3 施工步驟

| # | 步驟 | 產出 | 誰能做 |
| --- | --- | --- | --- |
| 1 | 勘查 SURVEY | 塊內 10×10 個點查 Street View metadata，選出最多 **100 個標記座標** | 不需要模型（免費） |
| 2 | 地圖參數 PARAMS | JSON：地貌、水位、植被密度、殘骸狀態、色調、地標、**8 種材質**、每個標記的一句說明、勘查筆記 | 能輸出文字的模型 |
| 3 | 標記座標場景圖 SCENE × k | 每個標記一張 16:9 的地面景像，以該點街景為構圖 | 影像（或 SVG） |
| 4 | 正射地圖底圖 TILE | 俯視、北朝上、剛好框住這一塊；世界地圖上看到的就是它 | 同上 |
| 5 | 3D 圖資 DSM | 與底圖對齊的灰階高度圖（黑＝最低、白＝最高） | 同上 |
| 6 | 材質貼圖 TEXTURE × 8 | 參數列出的 8 種材質，各一張可平鋪貼圖 | 同上 |

- **標記座標的選法**：只留塊內的全景、同一全景只算一次、從中心開始做 farthest-point 讓標記散開、
  鏡頭朝向塊中心。全景不到 100 個時，同一個全景轉 90°、180°、270° 再取，最多四個方向。
  沒有街景的地方（山區、海面）k = 0，只畫底圖、3D 與材質。
- **參數排在最前面**：一百張圖可能出自三家模型，參數是它們共同的「這裡長什麼樣」。
  模型回的 JSON 格式不對時**修正而不是拒絕**（夾回範圍、補足材質與標記說明）；完全解析不了就用預設值 ——
  施工不能卡死在第二步。
- **3D 用高度圖，不用網格模型**：影像模型畫得出灰階高度圖，畫不出可靠的 mesh；
  「正射底圖 + 對齊的高度圖」本來就是地圖做 3D 地景的標準做法（2.5D）。網站用 three.js 疊成 3D 預覽。
- **接縫**：畫底圖時，已完成的鄰塊（北東南西）底圖會一起送給模型，要求邊界上的河流、海岸線、道路延續。

### 2.4 施工引擎

`lib/server/builder.ts`。一次做一步：

1. 拿**租約**（有期限，不抱交易鎖 —— 一步要呼叫外部 API 幾十秒；工作者當掉，租約逾時自動失效）
2. 讀狀態（和頁面看到的是**同一份**推導 `lib/server/blocks.ts`）
3. 沒有下一步 → 撥付保存費與分攤、標記完成
4. 施工餘額 < 下一步估價 × 1.25 → 等錢
5. **此刻**排名最前、做得了這一步的模型 → 畫
6. 成功失敗都記一列 `steps`（帳由它加總）；成功的話正規化成 WebP 存進 `artifacts`

觸發：捐款入帳時用 `after()` 立刻在背景開工；排程（Vercel Cron 每分鐘 `/api/cron/build`、
自架用 `pnpm worker`）是安全網，輪流替每一塊做一步，避免一塊大工程卡住其他小額捐款的區塊。

失敗處理：失敗的那一次**照樣記帳**（上游可能已經收了輸入 token，參考影像也已經抓了）。
連續失敗 3 次暫停；金鑰被拒立刻暫停（那是平台的問題，不會自己好）。

## 3. 捐款

### 3.1 流程

```
捐款人在區塊頁填金額、選模型（可不選）、留言（可不留）
  → POST /api/blocks/[key]/donate        建立 PENDING 捐款，取得金流商付款頁
  → 金流商付款頁
  → 金流商 webhook /api/payments/[processor]/webhook   驗簽 → 入帳（拆帳）→ 背景開工
```

- **入帳只認 webhook**（驗簽之後），不認瀏覽器導回來的那一頁 —— 導回頁可以被偽造。
- 入帳是**冪等**的：金流商重送同一個通知，帳不會記兩次。
- webhook 回報的金額與訂單不符就拒收。
- 單筆最少 NT$30（再少的話手續費會比捐款還多），最多 NT$100,000。
- 已完成的區塊不再收捐款。

### 3.2 拆帳

```
總額 − 金流手續費（金流商回報的實際值；沒有就以費率估）
     − 稅金與規費（總額 × 稅率）
     − 退款與拒付準備（總額 × 準備率）
     = 淨額
```

捐款以新台幣收、成本以美元計。每一筆入帳時存下**當時的匯率**，之後匯率變了，過去的帳不變。
所有金額在資料庫裡是**微美元整數**（1 USD = 1,000,000）—— 捐款帳上不能有浮點誤差。

### 3.3 給 AI 的建議（留言）

每筆捐款可以附一句 ≤140 字的建議（例：「請讓河邊多幾隻白鷺」）。最近 5 則會放進該區塊之後每一步的提示詞。

留言是**不受信任的輸入**：它被放在世界觀正典**之後**、明確標成「建議」，並要求與規則衝突時忽略；
控制字元與換行拿掉、長度截斷、數量設上限 —— 一則留言不能變成一整段新的提示詞。

> 這是原始需求「透過對話要求 AI 調整」在捐款模式下的形式：施工中的地圖看不到，
> 所以無法對著圖來回對話；改成捐款人留下建議，AI 在後續步驟參考。

### 3.4 金流商：**待營運方決定**

目前只實作了**示範金流**（`PAYMENTS=demo`：按一下就當作付款成功，不收錢；網站上方會一直掛著示範模式橫幅）。
示範金流走的是和真實金流**同一條路**（付款頁 → 帶簽章的通知 → 驗簽 → 入帳），
接上真的金流商只需要實作 `lib/payments/types.ts` 的 `PaymentProvider`：

| 方法 | 做什麼 |
| --- | --- |
| `createCheckout` | 建立訂單，回傳付款頁網址與金流商訂單編號 |
| `verifyWebhook` | 驗簽、取出訂單編號、金額、**實際手續費** |

台灣常見選項：綠界 ECPay、藍新 NewebPay、TapPay。Stripe 的支援國家清單在撰寫時不含台灣（以其官方清單為準）。

## 4. 投票：依捐款金額加權

| 規則 | 理由 |
| --- | --- |
| **一筆捐款就是一張選票**，權重 = 那一筆的總額（扣手續費前） | 「依捐款金額比例」最直接的實作 |
| 捐款可以**不投票**；不投票的錢照樣施工，只是不參與決定 | 需求明訂 |
| 捐款人之後可以把自己在某一塊的**所有**捐款改投或撤回，但只在完工前 | 票只在施工期間有意義 |
| **每一步開工那一刻**計票 | 因此施工途中只要票數翻盤，下一步就換模型 —— 一塊地圖裡出現好幾種畫風，是設計的一部分 |
| 排名第一、**而且做得了這一步**的那一家畫 | GPT Image 只會出圖，「地圖參數」那一步交給排名下一家 |
| 同票依固定順位：Google → OpenAI → Anthropic | 公開、可預測，不是隨機 |
| 沒有任何有效的票 → 平台預設（`DEFAULT_PROVIDER`） | — |
| 投給**停用中**那一家的票照樣顯示，但不能贏 | 把它從畫面上拿掉，捐款人會以為票不見了 |

每一步都記下開工時的排名快照（`steps.tally`）—— 「這一步為什麼是它畫的」永遠查得到。

投票面板對每一家顯示「若之後全部由它來畫，完成這一塊約需募得 NT$…」，讓捐款人知道選擇的代價
（Claude 的向量插畫 token 用量多，一塊約是另外兩家的三倍）。

### 4.1 三家模型

| 公司 | 模型 | 畫出來的是 | 參數（文字） |
| --- | --- | --- | --- |
| Google | Gemini 3.1 Flash Image（`gemini-3.1-flash-image-preview`） | 寫實影像 | ✓ |
| OpenAI | GPT Image 2（`gpt-image-2`） | 寫實影像 | ✗（交給下一家） |
| Anthropic | Claude Opus 5.5（`claude-opus-5-5`） | **向量插畫**（SVG → 伺服器點陣化） | ✓ |

- Claude 不輸出點陣影像。它看得懂參考照，然後寫出 SVG；伺服器淨化（拿掉腳本、事件、外部參照、
  foreignObject、DOCTYPE）後點陣化成 PNG。資料庫裡從來不存 SVG，網站也從來不送 SVG 給瀏覽器。
- Claude 開啟伺服器端 fallback（`fallbacks: "default"`）：安全分類器誤擋時由另一個模型接手，
  帳記在**實際服務的模型**身上。
- 平台設了哪一家的金鑰，哪一家才可投（`GEMINI_API_KEY`、`OPENAI_API_KEY`、`ANTHROPIC_API_KEY`）。

## 5. 預算書

每一塊都有一份預算書（`lib/world/budget.ts`），每一行寫明算法。各行加總 = 換算金額（募款總額）。

### 5.1 五組支出

| 組 | 項目 | 依據 | 預設參數 |
| --- | --- | --- | --- |
| **建設（Token）** | 地圖參數 | 該步 token × 模型費率 | — |
| | 標記座標場景圖 ×100 | 同上 | — |
| | 正射地圖底圖 | 同上 | — |
| | 3D 圖資（高度圖） | 同上 | — |
| | 材質貼圖 ×8 | 同上 | — |
| **參考資料** | 參考影像費 | Street View 每千張 US$7、地圖靜態圖每千張 US$2；metadata 免費 | — |
| **預備** | 失敗重試準備 | 剩餘 token 成本 × 比例 | 10% |
| | 匯率與價格波動緩衝 | 剩餘建設成本 × 比例 | 5% |
| **保存與營運** | 地圖資料 4 年保存 | 容量 × 副本 × 單價 × 48 個月 + 瀏覽傳輸 | 2 份副本、US$0.015/GB‧月、2,000 次瀏覽 × 5 MB × US$0.01/GB |
| | 伺服器運算與資料庫分攤 | 每塊固定 | US$0.25 |
| | 平台管理費 | 以上合計 × 比例 | **0%**（不抽成） |
| **收款成本** | 金流手續費 | 總額 × 費率 + 每筆固定費（含電子收據） | 2.8% + NT$5 |
| | 稅金與規費 | 總額 × 稅率 | 5%（營業稅） |
| | 退款與拒付準備 | 總額 × 比例 | 1% |

所有參數可用環境變數覆寫（`lib/server/config.ts`，見 `.env.example`）。
不合理的值（負數、比率 ≥ 100%）會被忽略、退回預設 —— 一個打錯的環境變數不該讓預算書變成 NaN。

### 5.2 補齊的項目與理由

需求列出的是：金流手續費、法定稅金或規費、地圖資料 4 年保存、100 張場景圖、3D 圖資、材質貼圖、其他地圖參數。
另外補上：

| 補上的 | 為什麼必須有 |
| --- | --- |
| **正射地圖底圖** | 地圖本身。沒有它，世界地圖上沒有東西可貼；3D 也沒有顏色 |
| **參考影像費** | 每張場景圖都要抓一張街景，是真的要付給 Google 的錢 |
| **失敗重試準備** | 被擋、截斷、沒回圖的那一次照樣計費 |
| **匯率與價格波動緩衝** | 成本是美元、捐款是台幣；模型也可能在施工期間調價 |
| **退款與拒付準備** | 信用卡爭議款與誤捐退款 |
| **伺服器運算與資料庫分攤** | 施工排程、影像轉檔、帳務與四年的資料庫保存 |
| **平台管理費（0%）** | 明列為 0，讓「捐款全數用在這一塊」是一個看得到的承諾，而不是沒寫 |

### 5.3 算法上的幾個決定

- **收款成本倒推（gross-up）**：淨額需要 X，總額得募到 `(X + 筆數 × 固定費) ÷ (1 − 手續費率 − 稅率 − 準備率)`；
  筆數依平均每筆金額（預設 NT$300）估，迭代收斂。已收的部分以實際扣款為準。
- **預備只對還沒做的步驟提列**：已完成的步驟沒有不確定性。失敗掉的實際花費列在「失敗重試準備」的實際欄，不重複算進建設行。
- **保存與分攤先圈存**：捐款淨額先圈出這兩筆（金額很小），剩下才是施工餘額；完工時一次撥入保存基金。
- **結餘**：超募時多的錢列為「預計結餘」，**不算進換算金額** —— 否則捐得愈多「所需」就愈高。完工後保留在該區塊帳上，作為日後整修或延長保存之用。
- **估計會愈來愈準**：同一個模型、同一種步驟累積 3 筆以上實際紀錄後，估計改用實際平均取代表上的先驗。

| 全部由 | 預計所需 Token | 換算金額 |

| OpenAI · GPT Image | ≈ 45 萬 | ≈ NT$358 |

## 6. 世界觀與一致性

`lib/world/bible.ts`。每一次繪製都放在提示詞最前面（英文，三家模型對英文的遵從度較好）：

- 人類在一千年前離開，原因不明；植物收復一切（濕熱地區：榕樹氣根、樹蕨、竹、藤蔓、苔）
- 鋼筋混凝土多已坍成長滿植物的土丘；高樓只剩掏空的骨架；沒有玻璃；鋼鐵鏽成紅褐色痕跡
- 道路成為林間直線空地或淺溪；橋只剩橋墩；低地淹成沼澤與湖；海平面略高
- **禁止**：人、文字、標誌、浮水印、完好的車輛、任何仍在運作的東西
- **地理要認得出來**：同樣的河、海岸線、山與街道格局
- 距臺北 101 六公里內加上地標正典：101 仍然站著，上段三分之一坍塌，只剩核心筒與八根巨柱

正典改版要 bump `BIBLE_VERSION`；每一步都記下用的版本。

## 7. ★ 風險與待決事項（上線前必須處理）

| # | 事項 | 狀態 | 需要誰 |
| --- | --- | --- | --- |
| 1 | **Google Maps 平台條款**：條款中「不得以 Google Maps 內容建立內容」（No creating content from Google Maps Content）明列 Street View。把街景交給 AI 轉繪、再以捐款營運，很可能落在這一條上 | 依需求實作了 Google 來源；只存全景 ID、不存影像；`ReferenceSource` 介面可換來源 | **法務**。替代來源：Mapillary（CC BY-SA 街景）、OpenStreetMap（ODbL 圖資） |
| 2 | **金流商** | 只有示範金流 | **營運方**選定並提供商店帳號 |
| 3 | **稅務與名目**：「捐款」在台灣若屬公益勸募，受公益勸募條例規範；若是營業人收取的贊助或服務費，則為營業稅銷售額。預設以 5% 營業稅計 | 稅率可調 | **會計師／法務**確認營運主體身分與名目（「捐款」或「贊助」） |
| 4 | **模型價格與型號**：費率與型號來自第三方彙整（官方頁面在開發環境連不到）；`gemini-2.5-flash-image` 據報已於 2026-10-02 停用，故預設用 3.1 | 集中在 `lib/world/pricing.ts`，改價要 bump `PRICING_VERSION` | 上線前對照官方價目表 |
| 5 | **影像儲存**：目前存在 Postgres（`bytea`）。一塊約 35 MB，長期應改物件儲存（保存費預設即以 R2 級單價估） | 可運作，未最佳化 | 工程 |
| 6 | **內容審核**：留言可能夾帶不當要求；模型可能畫出不當內容 | 留言當建議處理；三家各自有安全過濾；暫停機制 | 營運方決定是否加人工審核 |
