### M0 實作中發現、值得記下的事

| 發現 | 處置 |
| --- | --- |
| React Compiler 的 purity lint 擋下 render 中的 `Date.now()` | 這規則是對的，且與 P1「時間權威來自伺服器」一致。抽出 `lib/time.ts` 的 `serverNow()` / `withServerTime()` |
| Neon 的 `neon-http` driver **不支援交易** | Auth 與唯讀查詢照用；M2 的結算路徑必須改用 `neon-serverless` 的 WebSocket pool。已記在 `07` §1 |
| 遊戲曆用小數月份換算天數會有浮點誤差 | 剛好落在遊戲日邊界時會少算一天。改為全程整數毫秒運算 |
| `CHECK (taken <= capacity)` 讓登記併發控制退化為一句原子 UPDATE | 已寫入 schema，不需要 advisory lock |
| `docs/16` §4.1 的固有防禦實例算錯了 | 例子說「Lv5 據點 100 駐軍能擊退 50 劍士，因為攻方士氣 0.6」——但防守方**人口比較多**，士氣是 1.0，根本不打折。實際上 45 名劍士會輸、46 名慘勝（存活 0.5%）。已改寫該節：早期固有防禦不是「擊退」，是**讓交換比貴到不值得** |
| 最短行軍（180 s）時，哨塔預警的 300 s 下限會早於出發時間 | 真的會出現「敵人還沒出發，你已經看到來襲警報」。`warningWindow()` 加上 `Math.min(window, marchSeconds)` clamp，並寫成測試 |
| 賽季模擬找出 4 個數值表錯誤與 1 個結構性失衡 | 主堡建造時間與文件敘述差 2.6 倍、儲存上限漏算前哨營導致主堡 Lv28–30 不可達、人口上限公式與表格不一致、領土容量超出目標；以及**經濟在遊戲月 6–7 就完全飽和**。全部已修，詳見 `11` §12 |
| **M1a：三項公平性驗證在數學上不可能成立** | `13` §3 的 (b) 極差 < 20 格（環帶寬度就有 25–33 格）、(c) 鄰居數極差 ≤ 2、(d) 高價值地形標準差 < 12%（叢聚地形實測 87%）。前兩項改量離散度；(d) 的解法是**讓分配器看得見公平性檢查**——換 seed 永遠沒用，因為問題在選點不在地形。見 `11` §13.1 |
| **M1a：遺跡放置需要第四條約束** | 只用 `01` §4 的三條，40 次擺放的陣營面積差異中位數 48.7%，通過 5% 門檻的次數是 0。加上「三角形重心 ≤ 30 格」並在候選中挑最平衡的一組才穩定。見 `11` §13.2 |
| **M1a：Dijkstra 的距離陣列不能用 Float32** | 捨入後的值可能大於實際值，同一條邊會被無限重複鬆弛，整個 Voronoi 不收斂（會直接掛住）。改 Float64 並加惰性刪除 |
| **士氣不該套用在 PvE 上** | 反霸凌機制原本只對遺跡戰關掉。帶 200 兵打 40 人的營地被折到 0.57 倍，清營地變成穩賠——而營地是新手唯一的成長管道。`isRuinBattle` 改名為 `skipMorale`，遺跡戰與 PvE 共用。見 `11` §15.1 |
| **PvE 差點把 PvP 整個擠掉** | 第一版給營地一份獨立的注意力，秋冬戰鬥佔比從 95% 掉到 63%。玩家只有一支軍隊、一個晚上——改成共用一份注意力、掠奪優先評估、不划算才去打營地，季節節奏就自己出來了。見 `11` §15.2 |
| **招兵排在建設之後，拿的是吃剩的資源** | 木材是所有建築的通用材料，早期永遠見底，招募上限每小時都卡在「木材只夠招 0–3 個」。真實玩家是先扣下那份資源再去蓋東西。見 `11` §15.1 ③ |

## 相依關係

```
M0 ──┬─→ M1 ──┐
     └─→ M2 ──┴─→ M3 ──→ M3b ──┬─→ M4 ──→ M4b ──┐
                                └─→ M5 ──┬─ M5b ─┤
                                          ├─ M5c ─┤
                                          └─ M5d ─┴─→ M6 ──→ M7
```

M1（地圖）與 M2（經濟）可並行。
M5b（登記輪替）、M5c（AI）、M5d（遺跡軍團）在 M5 之後可並行。

M3（戰鬥）是關鍵路徑上風險最高的一段，建議先做戰鬥引擎的純函式與單元測試，
再接 UI。

**不可延後到 M6 的兩項**：

- **M5c（AI）**：AI 是 600 人密度的前提，而密度決定整個賽季弧線
- **M5d（遺跡軍團）**：它是「用兵高峰在秋冬」的主要引擎。
  沒有它，秋冬的戰鬥量驗證（`16` §10）根本跑不出來

**M3b（補給與區域容量）緊接 M3**：戰鬥引擎與容量機制是耦合的，
分開驗證會漏掉超限損兵與戰鬥結算的交互。
