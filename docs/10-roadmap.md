### M0 實作中發現、值得記下的事

| 發現 | 處置 |
| --- | --- |
| React Compiler 的 purity lint 擋下 render 中的 `Date.now()` | 這規則是對的，且與 P1「時間權威來自伺服器」一致。抽出 `lib/time.ts` 的 `serverNow()` / `withServerTime()` |
| Neon 的 `neon-http` driver **不支援交易** | Auth 與唯讀查詢照用；M2 的結算路徑必須改用 `neon-serverless` 的 WebSocket pool。已記在 `07` §1 |
| 遊戲曆用小數月份換算天數會有浮點誤差 | 剛好落在遊戲日邊界時會少算一天。改為全程整數毫秒運算 |
| `CHECK (taken <= capacity)` 讓登記併發控制退化為一句原子 UPDATE | 已寫入 schema，不需要 advisory lock |
| `docs/16` §4.1 的固有防禦實例算錯了 | 例子說「Lv5 據點 100 駐軍能擊退 50 劍士，因為攻方士氣 0.6」——但防守方**人口比較多**，士氣是 1.0，根本不打折。實際上 45 名劍士會輸、46 名慘勝（存活 0.5%）。已改寫該節：早期固有防禦不是「擊退」，是**讓交換比貴到不值得** |
| 最短行軍（180 s）時，哨塔預警的 300 s 下限會早於出發時間 | 真的會出現「敵人還沒出發，你已經看到來襲警報」。`warningWindow()` 加上 `Math.min(window, marchSeconds)` clamp，並寫成測試 |
| 賽季模擬找出 4 個數值表錯誤與 1 個結構性失衡 | 主堡建造時間與文件敘述差 2.6 倍、儲存上限漏算前哨營導致主堡 Lv28–30 不可達、人口上限公式與表格不一致、領土容量超出目標；以及**經濟在遊戲月 6–7 就完全飽和**。全部已修，詳見 `11` §12 |
| **M1a：三項公平性驗證在數學上不可能成立** | `13` §3 的 (b) 極差 < 20 格（環帶寬度就有 25–33 格）、(c) 鄰居數極差 ≤ 2、(d) 高價值地形標準差 < 12%（叢聚地形實測 87%）。前兩項改量離散度；(d) 的解法是**讓分配器看得見公平性檢查**——換 seed 永遠沒用，因為問題在選點不在地形。見 `11` §13.1 |
| **M1a：遺跡放置需要第四條約束** | 只用 `01` §4 的三條，40 次擺放的陣營面積差異中位數 48.7%，通過 5% 門檻的次數是 0。加上「三角形重心 ≤ 30 格」並在候選中挑最平衡的一組才穩定。見 `11` §13.2 |
| **M1a：Dijkstra 的距離陣列不能用 Float32** | 捨入後的值可能大於實際值，同一條邊會被無限重複鬆弛，整個 Voronoi 不收斂（會直接掛住）。改 Float64 並加惰性刪除 |
| **士氣不該套用在 PvE 上** | 反霸凌機制原本只對遺跡戰關掉。帶 200 兵打 40 人的營地被折到 0.57 倍，清營地變成穩賠——而營地是新手唯一的成長管道。`isRuinBattle` 改名為 `skipMorale`，遺跡戰與 PvE 共用。見 `11` §15.1 |
| **PvE 差點把 PvP 整個擠掉** | 第一版給營地一份獨立的注意力，秋冬戰鬥佔比從 95% 掉到 63%。玩家只有一支軍隊、一個晚上——改成共用一份注意力、掠奪優先評估、不划算才去打營地，季節節奏就自己出來了。見 `11` §15.2 |
| **招兵排在建設之後，拿的是吃剩的資源** | 木材是所有建築的通用材料，早期永遠見底，招募上限每小時都卡在「木材只夠招 0–3 個」。真實玩家是先扣下那份資源再去蓋東西。見 `11` §15.1 ③ |
| **M1b：地形不能「一格一個 sprite」** | 500×500 = 250,000 格，而 L3（2px/格）時整張圖都在畫面上。改成**每個 64×64 chunk 烘成一張 64×64 貼圖**（一格一像素），用一個 sprite 放大 `tilePixels` 倍 —— 配 `NEAREST` 取樣就是銳利的像素色塊。整張地圖因此永遠只有 **64 個 sprite**，再視野剔除到 1–9 個。這是整個渲染層唯一真正重要的決定 |
| **M1b：縮放吸附要用對數距離** | 層級是 2 / 8 / 32，等比不等差。用線性距離的話 5px 會吸到 2（3 vs 3 平手偏小），但幾何中點其實是 4 —— 手感明顯不對 |
| **M1b：縮放必須以手指之間那一點為錨** | 少了它，雙指縮放會從畫面中心脹縮，使用者想放大的東西會滑走。這是手機地圖最明顯的手感缺陷 |
| **M1b：WebGL 的畫面事後讀不回來** | `preserveDrawingBuffer` 預設 false，合成完 buffer 就丟了，E2E 想用 `drawImage` 讀像素一定拿到空白。開啟它會讓手機掉幀，所以 E2E 改成**比較相機移動前後的兩張截圖** —— 空畫布不會變，能證明的事情一樣 |
| **M1b：地圖是公開路由** | `/map` 原本放在需要登入的 `(game)` 群組下，E2E 全被導去登入頁。但地形 chunk 本來就是 CDN 上的公開靜態檔（`01` §3.2），而五項公平性驗證的數字要在封盤期公開（`13` §3）—— 想登記的人本來就該先看得到這一季的地圖 |
| **M2：事件被標記已結算，但效果沒套用** | 第一版的 `apply` 是恆等函式 —— 資源扣了、事件關了、主堡等級**沒動**。分段積分本來就是為了「速率在中途改變」而存在的，少了 `apply` 等於整個 `settle.ts` 白寫。補上 `lib/game/events.ts`，每套用一個事件就重算一次速率。見 `11` §16.2 |
| **M2：佇列不能另外存一張表** | 「目前在蓋什麼」如果既存在 `events` 也存在 `base_slots`，兩個真相遲早不一致 —— 而「遲早」就是**已到期但還沒被讀取結算**的那段時間。改成 `deriveQueues()` 從未結算事件推導，佇列變成事件表的一個 view |
| **M2：地形不能每次結算都去讀檔** | 設施產出要乘地形修正，但 `/lib/game` 不准有 I/O。加一個 `tiles.terrain` 欄位，佔領時從地圖靜態檔抄一次 —— 一格的地形整季不變，抄一次就夠 |
| **M2：拆除冷卻要從「下單」起算，不是「完工」** | 拆除要 3 小時，冷卻 6 小時。從完工起算的話實際冷卻是 9 小時，跟數值表對不上。`deriveQueues` 用 payload 裡的 `cooldownUntil` 反推下單時間 |
| **M2：集市的「日」是遊戲月，不是遊戲日** | 一個真實日 = 一個遊戲月，而遊戲日只有 48 分鐘。照遊戲日重置的話，`500 × 主堡等級` 的轉移上限一天會放行 30 次 —— 等於沒有上限 |
| **M2：日轉移上限要對交易雙方各算一次** | 只算賣方的話，小號互餵只要換個方向掛單就繞過去了。而且記帳的是「自己送出去的量」，兩邊數字本來就不同 |
| **M2：`useState` 的初始值只在掛載時採用一次** | 倒數計時器改用 `useServerClock(serverTime)` 之後，伺服器重新 render 給的新 `serverTime` 進不去已掛載的元件。回傳 `Math.max(ticked, serverTime)` —— 新的伺服器時間立刻生效，而且時間只會向前 |
| **M2b：「不開後門」逼出了一層抽象** | Server Action 的第一件事是從 session 解出 playerId，而執政官沒有 session。把**身分解析**與**規則驗證**切開成 `lib/server/base-ops.ts`，兩者共用同一條驗證路徑。AI 玩家與遺跡軍團之後也接在這裡 |
| **M2b：執政官不能接在頁面載入上** | 領主打開領土畫面正要點一塊 LODE，執政官搶先用那條佇列去拓最近的沼澤 —— 而它做的完全符合規則。觸發點改為純伺服器端（結算迴圈 + 2h 安全網），與 `18` §11.1 的敘述一致 |
| **M2b：安全網 tick 會自我繁殖** | 每次執行都排下一個 tick，而一次執行可能被多個到期事件觸發 → 幾小時後變成 tick 風暴。排之前先確認沒有未結算的 `STEWARD_TICK` |
| **M2b：`docs/18` §12 的「領土佇列閒置 < 15%」量錯了東西** | 實測休閒 56%、**積極玩家 58%**。閒置的成因是**資源**不是注意力，執政官補不了。檢查改為同時印出積極玩家的基準值，數字才讀得懂。見 `11` §17.2 |
| **M2b：方針的預設值必須是「全關」** | 預設開啟等於在玩家理解取捨之前就先幫他做了第一個決定。同理，`parseDirectives` 認不出來的欄位一律退回關閉 —— 格式演進時最壞情況應該是「執政官不動」，不是「拿舊參數亂花錢」 |
| **整合測試不需要容器** | PGlite 是編進 WASM 的 Postgres，跑在測試行程裡。`FOR UPDATE`、`ON CONFLICT`、`CHECK`、交易回滾全部是真的，而 CI 不用起任何服務。第一次啟動 + migration 約 3 秒 |
| **規劃與執行必須共用同一個可負擔性函式** | 執政官的募兵自己算了一次「買得起幾個」，漏掉 `checkTrain` 的「一次下的單不能超過倉庫容量」——於是它排出一個**保證失敗**的動作，每一輪都在簡報留一筆 BLOCKED。改成兩邊都用 `maxAffordable`。整合測試才抓得到這種分岔 |
| **人口要在「下單」時就扣，不是完成時** | 三條招募佇列各自下滿，總和會遠超過人口上限 —— 等到完成才發現超了，就只能在「憑空多出人口」與「白花資源」之間二選一。拓荒的民兵同理，召回時退還 |
| **像素頭像要左右對稱** | 只算左半邊再鏡射，隨機組合才會看起來像「一張臉」而不是一堆雜訊。刻意不對稱的部件（義眼、傷疤）在鏡射之後才畫上去。這是像素頭像生成最關鍵的一招 |
| **★ M3：跨玩家的事件塞不進 per-player 的 applier** | `settleWithin` 一次只鎖一位玩家，而 `apply` 的簽章是 `(economy, event) => economy` —— 那個 economy 只有一個人的。但戰鬥要**同時**改兩邊。硬塞進去就會出現「攻方結算時守方還沒被結算」這種必然算錯的狀態。所以行軍**不進 `events` 表**，由結算迴圈直接掃 `marches`（那張表本來就有 `arrivesAt` 索引）—— 少一層轉換，也少一個「事件被標記已結算但沒人套用」的陷阱 |
| **M3：抵達要依 `arrivesAt` 排序結算** | 同一格上兩支先後抵達的部隊，先到的要先打完。順序錯了，第二波會跟已經死掉的守軍交戰 |
| **M3：突襲的「損失 ×0.6」不能只折損失** | 折了損失卻不把「沒死成的人」加回存活者，等於憑空消失一批兵。`reviveSpared` 從原始編制反推存活數 |
| **M3：回程要用實際回去的那支部隊重算時間** | 打完之後慢的單位可能全死了。沿用去程時間會讓「全滅到只剩騎兵」反而回得比較慢 |
| **M3：召回不能是瞬間的** | 否則派兵完全沒有風險 —— 看到守軍太強就按一下取消。走了多遠就要走多遠回來 |
| **M3：偵查與戰鬥的隨機性要用 seed，不能用 `Math.random()`** | 結算會因為交易衝突而重試，而重試不該變成「再擲一次骰子」。`mulberry32(deriveSeed(marchId, ...))` |
| **M3：`starve()` 不擲骰** | 文件寫「隨機餓死 3%」，但結算必須冪等：同一個狀態算兩次要得到同一個結果。3% 是比例，不需要隨機 |
| **★ M5b：兩座據點的 2×2 核心可以疊在一起** | 出生點分配從 M1 起就會產生相距一格的兩個點，600 人裡有 20 位。唯一照得出來的症狀是「T=0 只寫進 2320 格 `BASE_CORE` 而不是 2400」—— 沒有錯誤、沒有例外，只有一位玩家的據點缺了一角。成因是九個桶 × 五個分層 × 小隊/散客各自呼叫 `poissonPick`，每次呼叫都只看得見自己挑的點。修法是一份跨呼叫的佔位表 + 把「硬性下限」與「理想間距」分開。見 `11` §20.4 |
| **M5b：硬性下限取 2 而不是 3** | 3 會把候選池需求從 `quota × 6` 推到 `× 18`，公平性檢查 (d) 從 2.8% 惡化到 28%。為了幾格呼吸空間讓一部分玩家系統性地生在比較好的地形上，那才是不公平。順帶發現原本寫死的「6 倍」本來就是 `2² × 1.5` —— 現在由 `HARD_MIN_SPACING` 推導，不會再各自漂移 |
| **★ M5b：數值表裡有係數、簽章裡有參數、預設值剛好是「沒有效果」** | 前線 +1 領土容量從 M0 就寫在 `SPAWN_BAND` 裡，`territoryCapacity(citadel, bandBonus = 0)` 也留了參數 —— 但四個呼叫端全部用預設值，那 120 位玩家的補償只存在於文件裡。這種組合會安靜地失效，而 `grep` 出來「所有呼叫端都沒傳」就是證據 |
| **M5b：T=0 不重跑地圖生成** | 「反正是確定性的」聽起來成立，但它讓「封盤公布的座標」與「真正開局的座標」變成兩次獨立計算 —— 生成參數差一點就分岔，而這種 bug 不會有人在測試環境撞到。改成封盤把座位表存進 `seasons.spawn_plan`，順便省掉在交易裡多開二十秒 |
| **M5b：封盤不能建立 `players` 列** | 否則資源從封盤那一刻就開始累積，早報名的人多賺 12 小時 —— 而「全員同時進入」是這整個設計的前提。整合測試驗的是「600 位玩家的 `settledAt` 只能有一個相異值」 |
| **M5b：賽季轉換與結算不共用同一分鐘** | 封盤要跑地圖生成（7–20 秒）、開賽要寫 600 位玩家，擠進 60 秒的 cron 預算會把所有人的佇列拖住。做了粗活就直接回傳，結算留給下一分鐘 |
| **M3：`settle.ts` 不該認識兵種** | 它只回報「糧食見底且收支為負持續了多久」，餓死哪些兵是 `army.ts` 的事。同一條界線的延續：那一層只做速率 × 時間的積分 |

## 相依關係

```
M0 ──┬─→ M1 ──┐
     └─→ M2 ──┴─→ M3 ──→ M3b ──┬─→ M4 ──→ M4b ──┐
                                └─→ M5 ──┬─ M5b ─┤
                                          ├─ M5c ─┤
                                          └─ M5d ─┴─→ M6 ──→ M7
```

M1（地圖）與 M2（經濟）可並行。
M5b（登記輪替）、M5c（AI）、M5d（遺跡軍團）在 M5 之後可並行。

M3（戰鬥）是關鍵路徑上風險最高的一段，建議先做戰鬥引擎的純函式與單元測試，
再接 UI。

**不可延後到 M6 的兩項**：

- **M5c（AI）**：AI 是 600 人密度的前提，而密度決定整個賽季弧線
- **M5d（遺跡軍團）**：它是「用兵高峰在秋冬」的主要引擎。
  沒有它，秋冬的戰鬥量驗證（`16` §10）根本跑不出來

**M3b（補給與區域容量）緊接 M3**：戰鬥引擎與容量機制是耦合的，
分開驗證會漏掉超限損兵與戰鬥結算的交互。
